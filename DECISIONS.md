# Design Decisions

Every non-obvious choice in this project, with the alternatives I rejected and what each choice costs. Format: **Context → Decision → Alternatives → Consequences**. The "Consequences" sections are deliberately honest about downsides — a design with no stated downsides hasn't been thought through.

---

## 1. Shard by `md5(account_id) mod N`

**Context.** One database becomes the write bottleneck. Accounts must be spread across several databases, and any process must be able to find an account's shard.

**Decision.** `shard = md5(account_id) mod N`. The account id is generated by the API (before insert) because it *is* the shard key. Routing is a pure function: no lookup table, no routing service, nothing to keep consistent.

**Alternatives.**
* *Directory/lookup table* (account → shard): flexible, but it is a new single point of failure and a new thing to keep consistent.
* *Range sharding* (by id/time range): easy range scans, but hot spots (all new accounts hit the newest shard).
* *Consistent hashing*: much better for adding shards; more machinery than this project needs.

**Consequences.** Even distribution (checked in `test_routing_spreads_evenly`) and zero coordination. **The cost:** changing `N` remaps most accounts, so resharding needs an offline/online data migration. `SHARD_URLS` order *is* the shard index — reordering the list silently re-routes accounts. Production fix: consistent hashing or virtual shards. md5 is used for speed and uniformity, not security.

## 2. Money is an integer number of minor units (paise/cents)

**Context.** Money maths must be exact.

**Decision.** Balances and amounts are stored as `BIGINT` minor units; conversion to/from decimal strings happens only at the API edge (`app/money.py`). The API rejects amounts with more than 2 decimal places instead of rounding.

**Alternatives.** `float` (cannot represent 0.10; rounding drift is a correctness bug). `NUMERIC/Decimal` in the DB (exact, but SQLite stores NUMERIC as float — which would have made tests on SQLite lie about Postgres behaviour).

**Consequences.** Exact on every database and `balance >= amount` is a trivial integer comparison. Cost: assumes 2-decimal currencies (no JPY/KWD); that's a stated limitation.

---

## 3. Balance changes use one atomic conditional `UPDATE`

**Context.** Two concurrent debits on one account. Read-modify-write loses an update: both read 100, both write 40.

**Decision.**
```sql
UPDATE accounts SET balance_minor = balance_minor - :amt, version = version + 1
 WHERE id = :id AND currency = :cur AND balance_minor >= :amt
```
`rowcount == 1` means it happened; `0` means it didn't (a follow-up `SELECT` only classifies *why*: unknown account / wrong currency / insufficient funds). A DB `CHECK (balance_minor >= 0)` is a second, independent safety net.

**Alternatives.**
* *`SELECT … FOR UPDATE` then update (pessimistic locking).* Correct on Postgres, but needs explicit lock handling, holds the lock across more round trips, and is a **no-op on SQLite** — so the single most important guarantee couldn't be tested in the fast suite. (My first attempt used this and exactly that problem surfaced.)
* *Optimistic concurrency* (read `version`, `UPDATE … WHERE version = :v`, retry on conflict). Fine for low contention; under a hot account it degenerates into retry storms.
* *`SERIALIZABLE` isolation.* Correct but pushes retry logic everywhere and costs throughput.

**Consequences.** Correct on every database, shortest possible lock hold, no retry loop, testable for real. The `version` column is incremented on every change but is informational (stale-read detection), not load-bearing. Cost: all updates to one account serialise on its row — a very hot account caps throughput (mitigation: sub-accounts / sharded counters).

**3a. Lock ordering for same-shard transfers.** A→B and B→A at once would take the two row locks in opposite orders and deadlock on Postgres. Same-shard transfers therefore always touch the two rows in a fixed order (by account id). Reordering is safe because any failure rolls the whole local transaction back. SQLite can't deadlock this way, so the real proof is the `postgres`-marked test run in CI.

## 4. Idempotency: unique constraint + request fingerprint, claim first

**Context.** Clients retry after timeouts; an upstream may deliver twice. A retry must not charge twice.

**Decision.** Every payment needs an `Idempotency-Key`. `transactions.idempotency_key` is `UNIQUE`. The transaction row is inserted **first**, in the same DB transaction as the money movement; whoever loses a race gets `IntegrityError`, rolls back (nothing from that attempt persists) and returns the winner's row (`200`, `Idempotent-Replay: true`). A SHA-256 fingerprint of the request body is stored; reusing a key with a *different* body returns `409`.

**Alternatives.** *Check-then-insert in application code* (or a Redis `SETNX` check): both are separate steps from the actual write, so two requests can both pass the check. The unique index is the only thing that makes the claim atomic with the write; a cache would at best be an optimisation in front of it.

**Consequences.** Concurrent duplicates provably charge once (12-thread test; Postgres test in CI). Business-rule rejections (insufficient funds…) are *not* recorded — the whole transaction rolls back, so the key isn't burned and the client may retry after a top-up. **Limitation:** the constraint lives on the debit shard, so key uniqueness is per-shard, not global; a real API should namespace keys per client/merchant.

## 5. Cross-shard transfers: saga + outbox, not two-phase commit

**Context.** Debit and credit accounts can live on different shards. Shards are separate databases with no shared transaction coordinator.

**Decision.** Same-shard: one ACID transaction (debit + credit + status + event). Cross-shard: a **saga**.
1. *Local ACID tx on the debit shard:* insert transaction as `PROCESSING`, debit, write a `transaction.debited` outbox row.
2. *Worker:* credit the destination in its own local ACID tx, then flip the transaction to `COMPLETED`. If the credit is impossible: roll back the credit, **refund the payer and flip to `FAILED` in one local tx** (compensation).

**Alternatives.**
* *Two-phase commit (XA).* Gives atomicity, but holds locks across both shards for the whole protocol, makes the coordinator a single point of failure, and one slow shard stalls everyone. It throws away most of what sharding buys.
* *One big transaction.* Impossible across separate databases.
* *Credit first, then debit.* Creates money out of thin air on failure — strictly worse than the reverse.

**Consequences.** High throughput and independent shard failure. **The cost, stated plainly:** between steps 1 and 2 the payer is debited, the payee isn't credited, and the transaction reads `PROCESSING`. The system is *eventually* consistent across shards, and no state exists where money is lost or created permanently (`test_invariants.py` audits this under load). Debit-first means a failure is repaired by a refund, never by clawing back a credit someone may already have spent.

## 6. Transactional outbox instead of "write DB, then publish"

**Context.** Step 1 must both change the database and emit an event. Doing those as two separate writes (the *dual-write problem*) can silently diverge: publish-then-crash loses the debit's consistency; commit-then-crash loses the event and the payment is stuck forever.

**Decision.** The event is written to an `outbox_events` table **in the same local transaction** as the business change. A separate relay reads unpublished rows, publishes them, then marks them published.

**Alternatives.** *Publish inside the request* (the dual-write bug). *Log-based CDC* (Debezium tailing the WAL): removes polling latency, but adds infrastructure. *Kafka transactions*: don't cover the database.

**Consequences.** An event can never be lost if the debit committed. Delivery is **at-least-once** (crash between publish and mark ⇒ republish), which forces idempotent consumers (#7). The polling relay adds up to one `OUTBOX_RELAY_INTERVAL_SECONDS` of latency. The relay uses short DB sessions and never holds a transaction open across network I/O.

---

## 7. At-least-once delivery + idempotent consumer = effectively-once

**Context.** Kafka and the relay can both deliver an event more than once.

**Decision.** The settlement credit and a `processed_events` marker (primary key `credit:<txn_id>`) are written in the **same** local transaction. A duplicate fails on the marker insert, so the credit isn't applied twice. The finalisation step is itself idempotent (#8). The consumer commits its Kafka offset only **after** the handler succeeds.

**Alternatives.** *"Exactly-once" broker semantics*: only cover broker-to-broker, not a side effect in an external DB. *Check-then-act on the balance*: racy.

**Consequences.** Safe against redelivery, crash between steps, and two workers handling the same event. A handler that keeps failing is retried (3×, backoff) then sent to a **dead-letter queue** (`<topic>.dlq`) so one poison message can't block a partition forever; DLQ draining is manual.

---

## 8. Transaction lifecycle as a conditional-UPDATE state machine

**Decision.** `PROCESSING → COMPLETED | FAILED`; both terminal. Legal moves live in one dict (`VALID_TRANSITIONS`). Changing state is `UPDATE … WHERE id=:id AND state IN (<legal sources>)`; it returns whether *this call* moved it, and side effects (refund, event) run only if it did.

**Alternatives.** *Load → check → set → commit*: two workers both see `PROCESSING` and both act (double refund).

**Consequences.** Re-processing an event, or two workers racing on it, is harmless; the refund happens exactly once because only the caller that flips the state performs it.

---

## 9. Transaction id encodes its shard: `<shard>-<uuid>`

**Decision.** Transactions live on the debit account's shard and their id starts with that shard index.

**Alternatives.** *Global transactions table* (a cross-shard bottleneck and a second source of truth). *Require the caller to send the debit account id on lookups* (leaks storage layout into the API).

**Consequences.** `GET /payments/{id}` routes with no extra lookup. Coupling: the id format is a contract that depends on `N` staying stable (see #1).

---

## 10. Event bus behind an interface; Redpanda in docker-compose

**Decision.** Application code depends on an `EventBus` protocol with two adapters: in-memory (default, tests, zero setup) and Kafka via `aiokafka`. `docker-compose` uses Redpanda — a single-binary, Kafka-API-compatible broker — so the demo needs one container instead of Kafka + ZooKeeper.

**Consequences.** The whole business-logic suite runs in ~2 s without Docker, while production uses the same code path with real Kafka (only env vars change). Cost: the in-memory bus can't reproduce real broker failure modes — those are tested by making `publish` itself fail, not by killing a broker. The Kafka adapter is not covered by automated tests here.

---

## 11. Circuit breaker around publishing

**Decision.** `CLOSED → OPEN` after N consecutive failures; fail fast while open; after a timeout go `HALF_OPEN` and allow one trial. The clock is injectable, so tests advance time instead of sleeping.

**Why it's safe.** While the breaker is open nothing is lost — rows just stay unpublished in the outbox (#6). The breaker only stops the relay from hammering a broker that is already down.

---

## 12. SQLite by default, Postgres in deployment

**Decision.** Defaults are 4 file-backed SQLite shards (WAL mode, 30 s busy timeout) so `pip install` + `pytest` works anywhere; `SHARD_URLS` switches to Postgres. CI runs the suite **and** the concurrency/deadlock tests against real Postgres.

**Consequences.** Fast, dependency-free development, and the guarantees are not tied to one engine because #3 avoids engine-specific locking. Cost: SQLite has one writer per file, so throughput numbers from SQLite are not production numbers (README says so).

---

## 13. Deliberately not built

Authentication/authorisation, rate limiting, FX and non-2-decimal currencies, a refunds/reversals API, metrics/tracing, Alembic migrations, consistent-hash resharding, CDC-based outbox. Each is a real production need; none changes the core correctness story above, and pretending to half-build them would weaken it.
